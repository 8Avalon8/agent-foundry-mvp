# 产品定位与 UX 原则

## 核心定位

Agent Foundry 的核心目标是做一个 Agent Builder：

```text
用户用自然语言说“我想做一个什么 Agent”
  -> Codex 把需求提交给本地 Agent Foundry 服务
  -> Web/A2UI 决策面板让用户确认关键设计
  -> 系统编译成 Agent Design Card、AgentSpec、工具策略、反馈策略和记忆策略
  -> Codex 读取结果并继续实现下一步
```

它不是 prompt 生成器，而是：

- Agent 蓝图生成器
- 人类反馈设计器
- 权限策略编译器
- 可交互配置界面

最终体验应该是：

```text
自然语言 -> Codex handoff -> Web/A2UI 决策面板 -> 用户确认 -> AgentSpec -> Codex 继续
```

而不是：

```text
自然语言 -> 直接生成一大坨 YAML
```

## Agent Builder 的职责

Agent Builder 像一个专业架构师，而不是问卷机器人。它应该：

1. 理解用户想创建什么 Agent。
2. 识别任务类型和风险等级。
3. 生成推荐配置组合。
4. 通过可交互面板让用户确认关键设计。
5. 把用户选择编译成 AgentSpec。
6. 生成可运行 Agent 模板。
7. 在运行后持续接收反馈，并提出规则更新建议。

当前 Agent Design Surface MVP 先完成创建 Agent 之前的设计闭环。真实 SVN runtime、真实公众号发布、自动 patch apply 和长期记忆自动合并是后续能力，不是当前主线。

默认行为：

```text
先给专业草案
再让用户低成本修正
最后生成结构化产物
```

## UX 原则

### 1. 先出草案，再问问题

不要一开始向用户抛出十几个开放问题。系统应该先表达理解和推荐：

```text
我理解你想做的是一个「SVN Review Agent」。
我推荐“受控半自动”模式：
- 自动读取 SVN diff
- 自动读取相关源码
- 测试命令运行前询问
- 不自动修改代码
- 输出 Markdown Review 报告
请确认下面 4 个关键决策。
```

### 2. 用户选择优先，自由输入补充

每个关键问题优先提供结构化选项，例如：

- 保守
- 平衡
- 高效
- 沙箱自治

同时允许自然语言补充：

```text
补充说明：我希望它可以读 src，但不能读 config/secret。
```

也就是说，交互形态是：

```text
结构化选择 + 自然语言补充
```

### 3. 每个推荐都要解释原因

不能只显示“推荐：B”。推荐必须给出原因：

```text
推荐：B. 受控半自动
原因：
- 这个 Agent 涉及代码审查，有一定风险。
- 只读模式太保守，质量可能不足。
- 高自治模式初期不安全。
- 因此建议自动分析，但写入和运行命令前询问。
```

### 4. 每个选择都要显示影响

用户选择之后，要看到它对 AgentSpec 的影响。例如：

```diff
tool_policy:
  shell.run_tests:
-   permission: deny
+   permission: ask
```

这会让用户明确感到系统是可控的。

### 5. 分阶段确认，而不是一次性大表单

复杂 Agent 不应该一次性确认全部配置。推荐阶段：

1. 基础目标
2. 自治程度和风险边界
3. 工具和权限
4. 人类反馈机制
5. 记忆和进化机制
6. 输出格式和 dry run
7. 生成 AgentSpec

每个阶段结束时生成 Agent Design Card。

### 6. 敏感动作必须显式审批

凡是涉及以下动作，都不能默认自动执行：

- 写文件
- 运行 shell
- 调用外部 API
- 发邮件
- 发布公众号
- 提交代码
- 修改长期规则
- 删除数据

权限模型至少要支持：

- `allow`：自动允许。
- `ask`：使用前询问。
- `deny`：禁止使用。

### 7. 进化必须通过 Rule Patch，而不是静默学习

Agent 可以提出：

```text
我发现你多次拒绝了这类建议，是否更新规则？
```

但不能偷偷修改长期行为。进化应该像 Git diff：

```diff
- 报告所有命名问题
+ 仅当命名问题影响业务理解或接口误用风险时报告
```

用户批准后，规则才可以写入 `learned_rules.md`、`style_rules.md` 或其他长期记忆文件。
